# М70 — минимальная QR-регистрация

Draft PR №2 содержит минимальный контур для прямой работы с основной Google
Таблицей М70:

- GitHub Pages непрерывно распознаёт QR камерой или по фотографии;
- авторизованное Apps Script web app открывает сканер и принимает результат;
- `Code.gs` ищет токен в F, проверяет статус в D и время в E;
- успешный проход записывает `Пришёл` в D и серверное время в E;
- повторный проход не меняет таблицу.

В этой версии нет отдельного хранилища, синхронизации и дополнительного журнала.
Код подготовлен для ревью и тестовой копии таблицы. Он не подключён к рабочему
Apps Script и не опубликован.

## Файлы

- `index.html` — интерфейс камеры, фотографии и состояния связи;
- `scanner.js` — очередь сканов, RSA-проверка bridge, offline/online и ручной
  повтор;
- `apps-script/Registrar.html` — авторизованное окно Apps Script;
- `apps-script/Code.gs` — allowlist, RSA-сессия и запись в D/E под `LockService`;
- `tests/` — клиентские, сетевые, bridge- и серверные тесты.

## Допустимые статусы

Новый проход разрешён только из одного из двух исходных статусов:

- `Зарегистрирован`;
- `Подтвердил`.

`Отменён`/`Аннулирован` возвращает `cancelled`, заблокированный билет —
`blocked`, резерв и любое другое состояние — `not_eligible`. Если в E уже есть
время или D уже равно `Пришёл`, сервер возвращает `already_used`.

Ни один отказ не меняет таблицу.

## Защита

`postMessage` не считается авторизацией. Рабочий запрос требует одновременно:

1. Входа регистратора в Google.
2. Совпадения email с server-side `REGISTRAR_EMAILS`.
3. Доступа регистратора к основной таблице при режиме `USER_ACCESSING`.
4. RSA-подписанной bridge-сессии сроком пять минут.
5. Совпадения `origin`, `window.source` и случайного `channelId`.
6. Повторной проверки allowlist в каждом серверном методе.

Токен передаётся только в памяти через проверенный bridge и
`google.script.run`. Он не помещается в URL, DOM, Git, ошибки или серверные логи.
Приватный RSA-ключ хранится только в Script Properties. В Git находится только
публичный ключ проверки.

`LockService.getScriptLock()` охватывает поиск, проверку и запись. Два телефона,
одновременно отправившие один билет, получают один `checked_in` и один
`already_used`; время записывается один раз.

## Поведение при потере сети

- Клиент ждёт ответ 15 секунд.
- Offline и timeout никогда не показывают успешный проход.
- Событие `online` не отправляет билет автоматически.
- QR, оставшийся в кадре, не создаёт новый запрос.
- Повтор возможен только кнопкой **Повторить отправку**.
- Ручной повтор использует прежний `requestId`.
- Поздний `checked_in` принимается не более одного раза и отменяет ещё не
  отправленный повтор.
- Счётчик подтверждений увеличивается только после положительного ответа Apps
  Script.

В этой минимальной версии сервер не хранит отдельный результат по `requestId`.
Если исходный запрос успел записать приход, а ответ потерялся, повтор безопасно
вернёт `already_used`, но не сможет доказать клиенту, был ли приход записан именно
первой попыткой. Проверка строки таблицы остаётся окончательным подтверждением.

## Резервное чтение фотографии

Кнопка **Выбрать фотографию QR** декодирует изображение тем же экземпляром
`html5-qrcode` и передаёт результат в тот же `onScanSuccess`. В авторизованном
режиме используется тот же server-side маршрут и те же проверки, что для камеры.
После обработки фотографии непрерывная камера запускается снова.

## Ручная настройка Google Apps Script

Эти действия выполняются владельцем только после отдельного подтверждения.

1. Однозначно определить production Apps Script project и записать его Script ID.
2. Сохранить текущий код, номер версии, deployment ID и рабочий URL `/exec` для
   отката.
3. Сначала создать отдельную тестовую копию основной таблицы с той же структурой
   D–F и только синтетическими токенами.
4. Перенести `apps-script/Code.gs` и `apps-script/Registrar.html` в отдельную
   тестовую версию проекта.
5. Создать Script Properties:
   - `SPREADSHEET_ID` — ID выбранной таблицы;
   - `SHEET_NAME` — точное имя листа;
   - `CHECKED_IN_STATUS` — `Пришёл` или фактическое рабочее значение;
   - `REGISTRAR_EMAILS` — два точных Google email через запятую;
   - `BRIDGE_PRIVATE_KEY` — production PEM-ключ, соответствующий публичному ключу
     в `scanner.js`.
6. Не копировать приватный ключ из интеграционного контура. До загрузки проверить
   соответствие production private/public key локально без вывода ключа.
7. Дать двум регистраторам минимально необходимые права на целевую таблицу.
   Для `USER_ACCESSING` им нужны права, позволяющие Apps Script записывать D/E.
8. Создать новую версию web app со следующими настройками:
   - Execute as: **User accessing the web app**;
   - Access: только вошедшие Google-пользователи или общий Workspace domain;
   - anonymous access запрещён.
9. Под каждым разрешённым аккаунтом один раз пройти OAuth consent и проверить
   `Session.getActiveUser().getEmail()` через обычный `healthCheck`.
10. Сначала выполнить все проверки на тестовой копии. Production deployment и
    основную таблицу не переключать без отдельного решения владельца.

## Безопасная read-only проверка реального билета

Эту проверку выполняет владелец из редактора Apps Script после подключения
отдельного рабочего проекта к основной таблице:

1. Временно создать Script Property `VALIDATION_TICKET_TOKEN` со считанным
   токеном одного выбранного реального билета.
2. Запустить `validateConfiguredTicketWithoutCheckIn()` из редактора.
3. Ожидать только одну категорию: `eligible`, `already_used`, `cancelled`,
   `blocked`, `not_eligible` или `not_found`.
4. Убедиться, что D и E выбранной строки не изменились.
5. Убедиться, что `VALIDATION_TICKET_TOKEN` автоматически удалено в `finally`.

Функция не возвращает ID, токен, ФИО, email или исходный текст статуса. Токен и
результат не копируются в PR, чат, логи или скриншоты.

## Проверка записи только на тестовой строке

1. В основной таблице владелец вручную создаёт отдельную строку:
   - A: `TEST-CHECKIN-001`;
   - D: `Зарегистрирован` или `Подтвердил`;
   - E: пусто;
   - F: новый синтетический токен, который не совпадает ни с одним реальным QR.
2. Временно создать Script Properties:
   - `TEST_TICKET_ID=TEST-CHECKIN-001`;
   - `TEST_TICKET_TOKEN=<синтетический токен тестовой строки>`.
3. Запустить `checkInConfiguredTestTicket()` из редактора.
4. Проверить результат `checked_in`, значение `Пришёл` в D и серверное время в E.
5. Запустить повторно только после повторного задания временных свойств и
   проверить `already_used` без изменения первого времени.
6. Убедиться, что оба временных свойства удалились автоматически.
7. После проверки удалить только тестовую строку по утверждённой ручной процедуре;
   реальные строки и токены не изменять.

Helper отказывает, если найденная строка не имеет точный ID `TEST-*`, поэтому
его нельзя использовать для записи прихода реального билета.

## Обязательные проверки перед подключением основной таблицы

Все сценарии выполняются на синтетических токенах или специально созданных
тестовых строках.

1. `Зарегистрирован` и `Подтвердил` дают один `checked_in` и заполняют D/E.
2. `Отменён`, `Аннулирован`, `Заблокирован`, `Резерв` и произвольный статус дают
   отказ без записи.
3. Повтор одного билета на одном и двух телефонах возвращает `already_used` и не
   меняет исходное время.
4. Один новый билет одновременно сканируется двумя телефонами не менее десяти
   раз на разных тестовых строках: в каждой паре ровно одна запись.
5. Два разных QR распознаются подряд без перезапуска камеры.
6. Фотография нового, отменённого и уже использованного QR проходит через тот же
   серверный путь.
7. После offline нет ложного успеха и автоматического повтора; ручной повтор
   использует тот же `requestId`.
8. Поздний ответ не создаёт повторный запрос и не увеличивает счётчик дважды.
9. Renewal после пяти минут не стирает последнее сообщение о билете.
10. Третий аккаунт, пустой active-user email и anonymous получают отказ.
11. Неверные `origin`, `source`, `channelId`, подпись или истёкшая сессия получают
    отказ.
12. На реальных iPhone Safari и Android Chrome проверяются popup, `window.opener`,
    Apps Script iframe, камера, блокировка экрана и смена сети.
13. Пробный поток 120 синтетических сканов выполняется двумя телефонами, затем
    число уникальных записей времени сверяется с серверными результатами.

Unit-тест не доказывает браузерную совместимость Apps Script iframe и popup.

## Блокирующие риски

1. В режиме `USER_ACCESSING` регистраторам нужен доступ к основной таблице. Это
   раскрывает им ФИО, email и другие персональные данные. Если такой доступ не
   утверждён ответственным за данные, эту минимальную схему нельзя запускать.
2. Production Apps Script project/deployment и production RSA-пара должны быть
   однозначно идентифицированы. Интеграционный приватный ключ не подходит.
3. Без серверного журнала `requestId` потерянный ответ даёт безопасный, но
   неоднозначный `already_used` при повторе.
4. Apps Script sandbox, popup и `WindowProxy` должны быть проверены на двух
   фактических телефонах.
5. До отдельного разрешения нельзя проверять код настоящим QR, потому что
   успешная проверка необратимо изменит D/E.
6. Работа зависит от доступности Google Apps Script, Sheets, CDN библиотеки и
   интернета. При ошибке система закрывается безопасно и не подтверждает проход.

## Локальная проверка

```sh
npm test
npm run check
python3 -m http.server 4173
```

Прямое открытие GitHub Pages не даёт доступа к серверу и работает только как
локальный счётчик уникальных QR. Рабочий режим начинается исключительно из
авторизованного Apps Script web app.

## Откат

До переключения сохранить предыдущие Apps Script version/deployment ID и SHA
GitHub Pages. При проблеме вернуть deployment к предыдущей версии и сделать
обычный revert-коммит Pages. Не использовать force-push и не очищать реальные
статусы или время массово.
